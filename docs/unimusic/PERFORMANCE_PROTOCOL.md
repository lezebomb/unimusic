# UniMusic 性能测量协议

状态：Phase 0 尚无可用 Android 构建/设备运行结果。以下是后续可复现的测量设计，**不包含性能提升结论**；结构检查、Gradle 耗时和网络下载耗时不能充当应用性能。

## 1. 条件与样本

每次记录：应用 commit/build type、设备型号/Android/内存、温度与电源模式、前后台状态、Wi-Fi/移动网络与延迟、平台/登录状态（不含账号凭据）、库/歌单规模、缓存状态、并发上限和限流策略。

先用 3～5 次探索运行定位明显问题；发布正式 P50/P95 时使用充分样本并给出 N 与原始分布，尾延迟样本不足时不报告稳定 P95。远端测试按平台限制分散执行，不以高频重复请求产生负载。冷缓存、暖缓存、首次安装/已迁移、Fake provider/真实平台结果分别报告。

测量数据记录在 `build/reports/unimusic-performance/<revision>/`；可分享报告只保留匿名计数和非敏感环境信息，删除 query 明文、cookies、签名 URL、账号标识与本地私有路径。

## 2. 指标定义

| 指标 | 起点 → 终点 | 方法 / 控制变量 | Phase 0 数值 |
| --- | --- | --- | --- |
| 冷启动 | 进程启动 → 首个可交互帧 | Macrobenchmark StartupTimingMetric；固定启动入口，区别迁移首次启动 | 未测 |
| 打开我的库 | 导航事件 → 首屏可交互列表 | Trace + Compose 帧；1k/10k/50k 元数据 fixture，比较全量/分页 | 未测 |
| 本地查询 | 引擎接收 normalized query → 首批本地命中 | elapsedRealtimeNanos；分冷热缓存与命中/不命中 | 未测 |
| 在线首批 | 提交 query → 第一批有效可展示结果 | 每源和全局计时；不把空批次/纯 loading 当成功 | 未测 |
| 完整聚合 | 提交 query → 当前页全部来源完成或超时 | 分别标出成功/超时/失败来源；不能把提前丢弃来源写为加速 | 未测 |
| 跨平台匹配 | 收到固定候选集 → 身份/拒绝决策 | 固定标注 fixture、候选量、算法版本；不含候选检索网络时长 | 未测 |
| 点击播放至首声 | 用户播放事件 → 音频开始输出 | Trace + Media3 AnalyticsListener 音频前进回调作为软件代理；精确声学延迟需回环采集，二者分开 | 未测 |
| 故障恢复 | 注入具体来源故障 → 合格备用源开始输出 | Fake network/受控失效 URL、异常类型、恢复进度/队列校验 | 未测 |
| 大歌单导入 | 任务开始 → 全部页成功/失败状态持久化 | 1k/10k fixtures；首批可见、总时长、请求数、重试/峰值并发 | 未测 |
| 内存峰值 | 同一场景运行窗口的 peak PSS/heap | Profiler/Perfetto；区分 native 解码内存与 JVM 分配 | 未测 |
| 后台功耗 | 固定播放场景窗口 | 真机 Battery Historian/Perfetto/电源工具；固定音量/输出设备/网络/时长 | 未测 |

探索目标保留用户给出的方向：缓存命中本地搜索尽量 <150ms，良好 Wi-Fi 首批在线结果 P50 尽量 <1s/P95 尽量 <2.5s。它们不是当前已达到的验收值，须由实际基线与平台预算修订。

## 3. 埋点和失败隔离

使用单调时钟记录 duration；同一操作以不含 PII 的 request/event UUID 关联。推荐区间：`library.first_page`、`search.local`、`search.provider.<id>`、`search.first_batch`、`search.page_complete`、`match.classify`、`match.decide`、`source.resolve`、`playback.audio_advance`、`import.page_commit`。跨线程 async trace 使用独立 cookie，避免 Trace section 不成对。

每条样本带 cache hit、结果数、候选数、来源状态与是否取消；取消的请求单独计数。网络故障、授权过期、限流、会员/区域限制和匹配拒绝不能混为高延迟成功。URL 解析只覆盖临播和必要备用来源，不能为降低“点击延迟”预解析整个搜索结果列表。

## 4. 按证据排序的优化候选

1. 对上游 `fetchFullPlaylistTracks` 增加批次并发限制和页级提交，测峰值请求数/内存/首批可见。
2. 比较当前单平台搜索与 Flow 首批增量模型，观察首批和完整聚合延迟，验证一个平台超时不阻塞其他来源。
3. 为严格匹配结果/用户映射建立合规 TTL 缓存，先验证正确性，再测召回与决策开销。
4. 自动切源首个合格结果先返回，备用源延后准备；测真实首声和恢复，避免首播等待所有 fallback。
5. 按实测查询计划为统一库添加索引/FTS，检查写放大和迁移代价，不仅测小样本命中。

每次优化保存同条件 before/after、样本 N、P50/P95、失败率和请求量；只跑单次或使用模拟延迟时明确说明，禁止把 Fake provider 的时序换成平台线上性能。

## 5. 匹配质量单独评估

标注集包含录音室原唱、同名不同曲、翻唱、Live、伴奏、Remix、变速/剪辑、不同发行/再录音和未知权限。标注来源与验证证据保留，训练/调阈值与评估集合分离；只对有权处理的音频使用指纹。

报告 `错误自动接受数 / 全部自动接受数`、自动覆盖率、拒绝率、按版本/平台分组和样本量/不确定性。没有自动接受时错误率不可按 0% 报告；合成单测只能验证规则，不能支持真实错误自动匹配率 <1% 的结论。当前无已执行人工标注评估，因此无达标结论。
