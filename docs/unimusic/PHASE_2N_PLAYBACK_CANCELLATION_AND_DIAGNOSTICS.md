# Phase 2N：取流取消与失败诊断

日期：2026-10-27。基线 `ba5bb77d`；Room 仍 v23，没有数据迁移或清库。上一阶段 [CI](https://github.com/lezebomb/unimusic/actions/runs/40462851633) 已确认成功。

## 实现

YouTube 的主页 bootstrap、player API 和 STS 文本请求原先使用同步 `Call.execute()`，现改为既有 `awaitResponse`：协程取消会取消底层 Call，包含读取响应体的阶段；单个请求限时 3 秒，超时转为网络超时异常。HTTP 错误仍保留状态码和 Retry-After，继续执行原有授权/限流处理，但不再把原始响应正文带入日志。

后台共享 bootstrap 和共享取流任务各增加显式 8 秒生命周期，避免它们独立于前台等待持续执行；前台普通解析原本就共享 8 秒预算，本轮没有声称修复不存在的“每次外层重试都重置预算”问题。运行时去掉了 YouTube 整套 client/locale 流程的外层重复启动，保留仓库内部有效重试和回退；B站重试策略未变。第三方同步 NewPipe/extractor/JS 求解器的硬截止尚未建立证据，不能把协作式超时说成全链路保证。

B站解析不再直接记录带签名的音频 URL。设备诊断只记录平台、HTTP 阶段名称、是否拿到地址、错误类别与时间，不输出响应、请求查询、Cookie 或账号信息。精确登记了新增 SocketTimeoutException 的依赖，未放宽整个 java.net 域。

## 实际结果

- 9 个直接相关 JVM 检查通过：3 个新检查覆盖请求截止取消底层 Call、调用方取消语义、HTTP 状态/Retry-After 与正文保密；4 个 bootstrap 检查和 2 个取流/预取共享检查保留。已加入精简 CI。
- 最终 Debug APK、AndroidTest APK、平台依赖及模块边界通过，两个 APK 已保留数据覆盖安装到 Mate60。首次边界检查缺少精确超时异常登记，补齐后通过，没有隐藏该次失败。
- 真机只执行两个方法，随改动诊断共 4 次：1 次 B站通过、3 次 YouTube 失败。原始基线与最终失败记录已保留，中间一次日志留在已忽略的 build 目录。
- YouTube 最终仍没有取得地址或实际播放。观察到 bootstrap、player JS、player API 请求阶段；首次超时事件为 8684ms，结束时 pending=false，在 20 秒观察结束时共享客户端剩余 YouTube HTTP Call 为 0。这是单次事件/请求观察，不是成功取流或精确首声指标。
- B站样本本次播放请求到观察到进度为 2689ms，位置 2073ms；观察到地址变化为 162ms。该样本保留了之前的音频缓存，不能据此宣称冷启动从 10.9 秒优化到 2.7 秒。
- 正常 App 界面也检查了公开查询：聚合各平台返回结果，酷我首项标为音频地址已校验；选择 YouTube 公开歌曲后仍显示“无法获取播放地址”。搜索成功不作为音频成功，QQ 搜索结果也不作为账号取流验证。

最终哈希、命令日志位置、XML、原始设备输出和未执行项见 [validation.json](evidence/2026-10-27/phase2n/validation.json)。当前账号、导入歌单和充电常亮保留；播放已暂停，失败对话框已关闭。没有新短信、账号退出或 Gmail 连接。
