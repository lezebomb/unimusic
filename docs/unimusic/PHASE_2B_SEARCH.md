# Phase 2B：多来源聚合搜索与排序

日期：2026-10-26。接续 `bea4d48e`；其 [远端 CI](https://github.com/lezebomb/unimusic/actions/runs/40270887580) 已成功。按用户要求继续音源与搜索优先，未重装工具链，未修改 Room v22 或原有迁移。

## 搜索与获取行为

- 新增默认“聚合”入口，复用本地文件、网易云、B 站和已开启的 YouTube，单个平台/链接入口仍保留。这里增加的是多来源同时发现和选择能力，不是新增四个平台。
- 公共层的 `FederatedSearchProvider` 只接收查询、该源的游标并返回一页元数据；不允许搜索适配器预先解析播放地址。各平台仍保留自己的 SongItem 来源身份，点击结果走既有播放路径。
- Flow 按完成顺序发布批次，快源先显示；慢源、未登录、关闭或异常不清空其他源。最多并发 3 个来源，每个来源从排队开始最多 6 秒。这是可配置预算，不是实测搜索性能。
- 各源分别保存游标、已载条目、加载和失败状态；已结束的源不重复请求，暂时失败可显式重试。追加页保留已有条目并按来源稳定 ID 去重；重复游标会终止该来源翻页，防止无限循环。YouTube 目前仍受已有 API 首批 30 条限制，没有虚构 continuation 支持。
- 页面能看到每个源的已载数量、待登录、未开启、暂不可用与继续加载状态。有结果时不会被全屏加载遮住，失败有重试入口。
- 查询先做 NFKC 和空白规范化；复用已有曲名/歌手/专辑字段权重、拼音全拼/首字母和多词匹配。新增现场/翻唱/伴奏/混音/剪辑/变速等版本偏好，明确查询版本时保留相关结果。按稳定来源顺序交错批次后排序，避免相同相关性只由谁先返回决定。
- 本地仅搜索已有授权文件的库条目，在后台线程构造文本/拼音索引，同次查询翻页复用；没有扫描文件系统或请求额外权限。换新查询会构造新快照，尚未增加跨查询索引缓存。
- 不把同名、同歌手、相近时长的不同平台结果合并为同一录音；展示排序没有音源授权或自动匹配置信度含义。
- 网易云搜索改用已有可取消接口；登录预热不再进入阻塞 HTTP，账号更换后的旧响应被拦截。聚合查询在网易云账号身份变化或 YouTube 开关变化后重新开始，旧请求仍受 generation 检查。

## 实现入口与调研

- `modules/common/.../search/FederatedSearchEngine.kt`：Provider/分页/Flow 快照、并发与预算、错误隔离。
- `app/.../viewmodel/tab/ExploreViewModel.kt`：四来源适配、独立翻页、会话变化与旧请求丢弃。
- `app/.../viewmodel/tab/ExploreSongSearchRanking.kt`：复用文本匹配并增加版本排序；不做录音聚类。
- `app/.../screen/tab/explore/`：聚合入口、部分结果呈现与来源状态；补中文/英文文案。
- `modules/platform/.../netease/api/client/NeteaseClient.kt`：可取消预热与搜索会话绑定。
- [音源机制调研](MUSIC_SOURCE_RESEARCH.md)：MusicFree、LX、InnerTune、Spotube 的一手资料与可复用设计，未引入它们的代码或未知解析服务。
